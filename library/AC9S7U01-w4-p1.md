<!-- _header: '**Concept** Using a key and building a key' -->

:::: grid-2x1

> **USING A KEY**
>
> - Start with one organism
> - Follow the decisions to a name
> - The features are chosen for you

> **BUILDING A KEY**
>
> - Start with a set of names
> - Choose features that split the set into two clean groups
> - Repeat on each group until every organism is alone

::::

> Building reverses using: now YOU choose the features.

<!-- _class: rules -->
<!-- _header: '**Concept** Five rules for a decision point' -->

1. **ONE FEATURE** — each decision checks a single observable feature.
2. **TWO OPTIONS** — exactly two, never three.
3. **NO OVERLAP** — every organism fits one option and only one.
4. **NO OPINIONS** — use features anyone can see or count, not big or pretty.
5. **TEST THE SPLIT** — try every organism in the set before you commit.

<!-- Speaker note: [MINIMUM] From the node glossary: before committing a decision, test whether every organism can go to exactly one of the two options with no ambiguity. -->

<!-- _header: '**I Do: Worked Ex. 1** Choosing a feature that splits cleanly' -->

Set: magpie, kangaroo, frog, goanna, goldfish.

| Feature I try | What it does to the set | Use it? |
|---|---|---|
| Has feathers | Magpie on one side, the other four on the other | **Yes**: you can see it and it splits cleanly |
| Lives in water | Goldfish, and the frog, which lives in both | **No**: not reliable, and it overlaps |
| Is big | Depends who decides | **No**: an opinion |

<!-- _header: '**I Do: Worked Ex. 2** Writing the key: Key E' -->

| Step | (a) If the organism… | (b) If the organism… |
|---|---|---|
| **1** | has feathers → **Magpie** | has no feathers → go to 2 |
| **2** | has fur → **Kangaroo** | has no fur → go to 3 |
| **3** | has smooth, moist skin and no scales → **Frog** | has scales → go to 4 |
| **4** | has legs → **Goanna** | has no legs and has fins → **Goldfish** |

<!-- Speaker note: [MINIMUM] Each step removes one organism. That is a valid key, though a long one: the typical block shows how to improve a key after testing. Many other valid keys exist for the same set. -->

<!-- _class: rules -->
<!-- _header: '**You Do** Test your key with a peer' -->

1. **SWAP** — give your key, not your answers, to a partner.
2. **FOLLOW** — your partner uses the key to identify every organism.
3. **RECORD** — they write each path and answer, and mark any step where they hesitated.
4. **REPORT** — compare with your own answers and say which steps worked.

<!-- _class: callout-ok verdict-false -->
<!-- _header: '**Check** ✓ Answer' -->

**"A key that works for the organisms you tested it on will always work for any organisms."**

> **✗ FALSE**
>
> **Why?** A key is built for a particular set. A feature that splits one set cleanly can fail when new organisms are added: a new bird would also have feathers.

<!-- Speaker note: [MINIMUM] Node file misconception: features that work for one organism set but fail for another. -->

---

<!-- _class: rules -->
<!-- _header: '**Revise** Fixing a key after testing' -->

1. **DEAD END** — an organism fits neither option. Rewrite so every organism has a path.
2. **OVERLAP** — an organism fits both options. Sharpen the feature.
3. **VAGUE** — the feature depends on opinion. Switch to something visible or countable.

<!-- Speaker note: [TYPICAL: can drop] Typical width, from the node file: construct and refine a key for 10 organisms and document one revision made after peer testing. -->
